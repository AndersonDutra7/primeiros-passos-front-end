01var

Trocar var por const e let

TÉCNICA: USAR O ESCOPO CORRETO

var tem escopo de função e vaza para fora de blocos if/for. Use const para tudo que não vai ser reatribuído e let apenas quando realmente precisar mudar (ex.: contador de for).

Aqui nenhuma variável é reatribuída — todas viram const. O i do for indexado vai virar let agora, mas vamos eliminar esse for mais tarde.

03Constantes

Eliminar números mágicos com constantes nomeadas

TÉCNICA: SUBSTITUIR LITERAIS POR CONSTANTES

O 600 aparece duas vezes e o 10 aparece uma. Se a regra mudar (limite virar 720s, ou playlist comportar 20 músicas), você precisa caçar todos os literais. Constantes UPPER_SNAKE_CASE no topo do arquivo concentram a decisão em um único lugar.

Quem lê duracaoEmSegundos <= DURACAO_MAXIMA_SEGUNDOS entende a intenção sem precisar saber o valor.

04podeAdicionar

Extrair função podeAdicionarNaPlaylist(duracao)

TÉCNICA: EXTRAIR FUNÇÃO DE VALIDAÇÃO

A regra "a música cabe na playlist?" está espalhada em dois if idênticos. Quando uma regra de negócio aparece duas vezes, ela merece um nome próprio — uma função pura que recebe a duração e devolve true/false.

Função pura = mesma entrada, mesma saída, sem efeito colateral. É exatamente o tipo que Jest testa com facilidade — vai ser nosso primeiro alvo na Parte 2.

O essencial

Função pura: mesma entrada → mesma saída, sem efeito colateral. Ideal para Jest.

Anatomia de um teste Jest

test('descrição do que está sendo verificado', () => { expect(...).toBe(...) }). A descrição vira a frase que aparece no terminal quando passa (verde) ou falha (vermelho com diff).

T1toBe

Testes de podeAdicionarNaPlaylist

CASOS DE BORDA · toBe()

Função que retorna true/false testa-se com toBe. Os casos importantes são borda exata (na regra <= 600, o 600 deve passar e o 601 deve falhar) e casos confortáveis (1, 300) para garantir que o comportamento dentro do limite está correto.

Por que testar a borda? Bug clássico é trocar <= por <. Sem o teste do 600, o bug passa despercebido — a função continuaria aceitando 599 e rejeitando 601 normalmente, mas rejeitaria 600 silenciosamente.

tests/playlist.test.jsJS 
describe('podeAdicionarNaPlaylist', () => {

  test('duração 600 → true (limite máximo, inclusivo)', () => {
    expect(podeAdicionarNaPlaylist(600)).toBe(true)
  })

  test('duração 601 → false (1 segundo acima do limite)', () => {
    expect(podeAdicionarNaPlaylist(601)).toBe(false)
  })

  test('duração 1 → true (mínima razoável)', () => {
    expect(podeAdicionarNaPlaylist(1)).toBe(true)
  })

  test('duração 300 → true (valor confortável dentro do limite)', () => {
    expect(podeAdicionarNaPlaylist(300)).toBe(true)
  })

})

Rodando: npx jest --verbose. A saída mostra cada test com check verde se passou. Mude <= para < em src/playlist.js e rode de novo: o teste da borda 600 falha imediatamente — é exatamente o que queremos.

T2toEqual

Testes de criarMusica

COMPARAR OBJETOS · toEqual()

toBe vs toEqual: toBe compara identidade (===) — funciona para primitivos (números, strings, booleanos). toEqual compara estrutura — é o que usamos para objetos e arrays. toBe({...}) em objeto sempre falha porque dois objetos diferentes nunca são ===.

Verificamos que o objeto retornado tem exatamente as três propriedades esperadas. O caso da duração 0 mostra que criarMusica não filtra — só monta — a validação é responsabilidade de podeAdicionarNaPlaylist.

tests/playlist.test.jsJS 
describe('criarMusica', () => {

  test('retorna objeto com titulo, artista e duracao', () => {
    const resultado = criarMusica('Imagine', 'John Lennon', 183)
    expect(resultado).toEqual({
      titulo: 'Imagine',
      artista: 'John Lennon',
      duracao: 183
    })
  })

  test('duração 0 ainda monta o objeto (não filtra na construção)', () => {
    const resultado = criarMusica('Silêncio', 'Anônimo', 0)
    expect(resultado.duracao).toBe(0)
  })

  test('sempre contém as 3 propriedades esperadas', () => {
    const resultado = criarMusica('X', 'Y', 100)
    expect(Object.keys(resultado)).toEqual(
      ['titulo', 'artista', 'duracao']

})
T3spyOn

Testes de exibirPlaylist com jest.spyOn

ESPIONAR EFEITO COLATERAL

exibirPlaylist não retorna nada — o que ela faz é chamar console.log. Como verificar isso? Substituir console.log por um espião que registra cada chamada. É exatamente o que jest.spyOn faz.

Padrão recomendado: spyOn dentro de beforeEach e mockRestore dentro de afterEach — o espião é montado e desmontado a cada teste, sem vazar para os outros. mockImplementation(() => {}) evita que o output real apareça no terminal durante os testes.

tests/playlist.test.jsJS 
describe('exibirPlaylist', () => {
  let spy

  beforeEach(() => {
    spy = jest.spyOn(console, 'log').mockImplementation(() => {})
  })

  afterEach(() => {
    spy.mockRestore()
  })

  test('lista vazia → não lança erro nem chama console.log', () => {
    expect(() => exibirPlaylist([])).not.toThrow()
    expect(spy).not.toHaveBeenCalled()
  })

  test('uma música → log no formato "Artista — Título (Xs)"', () => {
    exibirPlaylist([{ titulo: 'Imagine', artista: 'John Lennon', duracao: 183 }])
    expect(spy).toHaveBeenCalledTimes(1)
    const linha = spy.mock.calls[0][0]
    expect(linha).toContain('John Lennon')
    expect(linha).toContain('Imagine')
    expect(linha).toContain('183s')
  })

})

toContain vs string exata: usar toContain em vez de comparar a string inteira deixa o teste robusto — se você decidir trocar — por - no template, o teste continua passando porque o que interessa é que os três pedaços de informação aparecem.
