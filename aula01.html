Seção 01

O que é o
Git?

Imagine criar um jogo, um site ou um aplicativo e, depois de algumas alterações, perceber que algo parou de funcionar. Você tenta voltar atrás… mas já não lembra exatamente o que mudou. O Git resolve exatamente esse problema, registrando cada etapa da evolução do projeto como um histórico de versões.

Entendendo o Git

O Git é um sistema de controle de versão distribuído. Ele permite registrar alterações em arquivos, acompanhar o histórico do projeto e recuperar versões anteriores sempre que necessário. Em vez de sobrescrever arquivos manualmente, o Git salva "fotografias" do projeto chamadas de commits, criando uma linha do tempo completa do desenvolvimento.

🧠 Analogia

Imagine um jogo que salva automaticamente seu progresso em vários pontos. Se algo der errado, você pode voltar para qualquer save anterior.

O Git funciona exatamente assim, mas para projetos de software. Cada commit representa um ponto de salvamento da aplicação.

Isso significa que você pode experimentar mudanças sem medo, porque sempre será possível retornar para uma versão estável do projeto.

Para que serve o Git?

O Git é utilizado para controlar alterações no código-fonte, organizar o fluxo de desenvolvimento e permitir que múltiplos programadores trabalhem no mesmo projeto sem perder informações importantes. Hoje ele é o padrão da indústria para versionamento.

💾
Salvar versões do projeto
Cada commit registra um novo estado da aplicação, permitindo acompanhar toda a evolução do código.
⏪
Voltar versões anteriores
Se algo quebrar, o Git permite retornar rapidamente para uma versão estável do projeto.
🌿
Trabalhar com branches
Branches permitem criar funcionalidades isoladas sem afetar a versão principal do sistema.
👨‍💻
Colaboração em equipe
Vários desenvolvedores podem trabalhar simultaneamente no mesmo projeto com segurança.
💡 Resumindo

O Git é a ferramenta responsável pelo controle de versões de um projeto. Ele registra alterações, organiza o histórico do código e permite recuperar qualquer versão anterior.

Enquanto o GitHub é uma plataforma online de hospedagem, o Git é o motor que faz todo o versionamento funcionar.

Seção 02

O que é o
GitHub?

Imagine que você está escrevendo um trabalho escolar em grupo. Cada pessoa edita uma cópia diferente do documento — e no final ninguém sabe qual é a versão certa. O GitHub resolve exatamente esse problema, mas para código.

Entendendo o GitHub

O GitHub é uma plataforma baseada em nuvem utilizada para hospedar repositórios Git. Ele permite armazenar código online, acompanhar alterações, colaborar em equipe e manter um histórico completo do projeto.

📦 Analogia

Pense no GitHub como um Google Drive para código, mas com superpoderes. Além de guardar seus arquivos online, ele guarda um histórico completo de todas as alterações — quem mudou o quê, quando e por quê. É como ter um "Ctrl+Z" infinito para todo o seu projeto.

Se o Google Drive salva versões automáticas de um documento, o GitHub deixa você criar versões intencionais — cada "save" é chamado de commit, e você escolhe o que salvar e escreve uma mensagem explicando a mudança.

Além disso, o GitHub permite que várias pessoas trabalhem no mesmo projeto ao mesmo tempo, sem sobrescrever o trabalho umas das outras — como um Google Docs, mas para programadores do mundo todo. 🌍

Para que serve o GitHub?

O GitHub vai muito além de apenas armazenar código online. Ele é utilizado para controlar versões de projetos, colaborar em equipe, registrar alterações, compartilhar soluções com outros desenvolvedores e até publicar aplicações na web. Atualmente, empresas do mundo inteiro utilizam o GitHub como parte fundamental do fluxo de desenvolvimento de software.

🗂️
Guardar seu código online
Seu projeto fica salvo na nuvem. Se seu computador queimar, você não perde nada — é só acessar sua conta e baixar tudo de volta.
📜
Histórico de versões
Cada commit é como uma foto do projeto naquele momento. Você pode voltar a qualquer versão anterior com um único comando.
👥
Trabalho em equipe
Vários devs podem trabalhar no mesmo repositório ao mesmo tempo, em paralelo, sem conflito — usando branches.
🌐
Portfólio público
Seus repositórios ficam visíveis para o mundo. Empresas usam o GitHub como currículo técnico de candidatos. ⭐
💡 Resumindo

O GitHub é uma plataforma web que hospeda repositórios Git. Ele adiciona uma camada social e colaborativa ao Git — pull requests, issues, Actions (CI/CD), Pages (hospedagem), e muito mais.

Hoje, mais de 100 milhões de desenvolvedores usam o GitHub. É a maior rede social de código do mundo — e saber usá-lo é uma habilidade fundamental para qualquer programador.

Seção 03

Git vs
GitHub

Essa é uma das maiores dúvidas de quem está começando. Apesar de trabalharem juntos, Git e GitHub não são a mesma coisa. Um é a ferramenta de versionamento. O outro é a plataforma online que utiliza essa ferramenta.

A diferença entre Git e GitHub

O Git é responsável por controlar versões e registrar alterações no projeto. Já o GitHub funciona como uma plataforma online para armazenar, compartilhar e colaborar em repositórios Git. Em outras palavras: o Git é o motor do versionamento, enquanto o GitHub é a plataforma onde esses projetos podem ser publicados e acessados pela internet.

🚗 Analogia

Pense no Git como o motor de um carro. Ele faz toda a parte técnica funcionar: registra versões, acompanha mudanças e organiza o histórico do projeto.

Já o GitHub seria uma garagem inteligente na nuvem, onde você guarda, compartilha e mostra seus projetos para outras pessoas.

Você pode usar o Git sem GitHub — mas o GitHub existe justamente para potencializar o uso do Git em equipe e na internet.

Comparando Git e GitHub

Embora estejam diretamente relacionados, Git e GitHub possuem papéis diferentes dentro do fluxo de desenvolvimento de software. A tabela abaixo resume as principais diferenças.

🙋 Dúvidas Frequentes
🤔 Preciso instalar o Git para usar o GitHub?
▼

Para usar a interface web do GitHub, não. Você pode criar repositórios, editar arquivos e até fazer commits diretamente pelo navegador, sem instalar nada.

Porém, para usar o Git via terminal (linha de comando) — que é o jeito profissional — você precisa instalar o Git no seu computador. Acesse git-scm.com e baixe para o seu sistema.

🔧 Existem alternativas ao GitHub?
▼

Sim! O Git pode ser usado com outras plataformas de hospedagem, como GitLab (muito usado em empresas, com CI/CD embutido) e Bitbucket (integrado ao ecossistema Atlassian — Jira, Confluence). O GitHub é o mais popular, especialmente para projetos open source.

💰 GitHub é pago?
▼

O plano Free do GitHub é gratuito e suficiente para a maioria dos estudantes e projetos pessoais. Com ele você tem repositórios públicos e privados ilimitados, GitHub Pages (hospedagem de sites estáticos), GitHub Actions (2.000 minutos/mês de automação) e muito mais.

Os planos pagos (Pro, Team, Enterprise) adicionam recursos avançados para times e empresas.

💡 Resumindo

O Git é a ferramenta responsável pelo controle de versões. O GitHub é a plataforma online que utiliza Git para armazenar e compartilhar projetos.

Eles trabalham juntos — e dominar essa dupla é um dos primeiros passos para atuar profissionalmente no desenvolvimento de software.

Seção 04

O Fluxo
Básico

Todo projeto utilizando Git + GitHub segue um fluxo relativamente simples. Aprender essas etapas é o primeiro passo para entender como desenvolvedores organizam alterações, salvam versões e compartilham código profissionalmente.

Entendendo o Fluxo Básico

O fluxo de trabalho com Git e GitHub segue uma sequência lógica: criar arquivos, registrar alterações, salvar versões e enviar o projeto para a nuvem. Esse processo permite acompanhar toda a evolução do sistema, organizar o desenvolvimento e colaborar com outros programadores de forma segura.

01
📁 Criar Projeto Local
O primeiro passo é criar uma pasta no seu computador para organizar os arquivos do seu novo projeto e navegar até ela pelo terminal.
criar pasta do projeto 
# Criar uma nova pasta
mkdir meu-projeto
# Entrar na pasta criada
cd meu-projeto
02
⚙️ Inicializar Git
Para que o Git comece a rastrear as mudanças nessa pasta, você precisa transformá-la em um repositório local.
inicializar o repositório 
# Inicializar o Git na pasta atual
git init
Initialized empty Git repository in /meu-projeto/.git/
03
🌐 Criar Repositório no GitHub

Agora vamos preparar a "nuvem" para receber seu código. Siga a sequência abaixo diretamente no seu perfil do GitHub:

1. Inicie um novo repositório

No seu painel do GitHub ou na aba "Repositories", localize e clique no botão verde New.

2. Configure as informações básicas

No campo Repository name, digite o nome do seu projeto (sem espaços ou acentos). Certifique-se de que a opção Public está marcada e role até o final para clicar em Create repository.

3. Tela de Quick Setup

O GitHub criará o repositório e te mostrará a página de instruções. Note que ele já te oferece os comandos de git remote add e git push que usaremos a seguir. Copie a URL (o link que termina em .git).

⚠️ Atenção: Nesta etapa, prefira não inicializar com README, .gitignore ou Licença. Isso garante que o repositório comece vazio e evita conflitos quando você for conectar seu projeto local que já possui arquivos.
04
🔗 Conectar Projeto ao GitHub
Agora você precisa dizer ao seu Git local para onde ele deve enviar o código na internet. Vamos vincular a URL copiada ao apelido padrão de origin.
vincular repositório remoto 
# Conectar o repositório local ao GitHub
git remote add origin https://github.com/usuario/meu-projeto.git
05
✏️ Editar Arquivos
Abra os arquivos no seu editor preferido (como o VS Code) e faça as alterações necessárias. O Git rastreia automaticamente qualquer nova linha ou arquivo adicionado.
💡 Use git status a qualquer momento no terminal para ver quais arquivos foram modificados ou criados.
verificar status do repositório 
# Verificar o estado atual dos seus arquivos
git status

# Retorno do terminal mostrando arquivos modificados e não rastreados:
On branch main
Changes not staged for commit:
  (use "git add <file>..." to update what will be committed)
  modified:   index.html

Untracked files:
  (use "git add <file>..." to include in what will be committed)
  styles.css

no changes added to commit (use "git add" and/or "git commit -a")
06
📸 Adicionar e Commitar (Tirar a Foto)
Antes de salvar, você prepara os arquivos com git add. O commit funciona como uma fotografia oficial do estado do seu projeto naquele momento.
preparar e salvar 
# Adicionar todos os arquivos modificados ao stage
git add .

# Salvar a versão com uma mensagem descritiva
git commit -m "feat: estrutura inicial do projeto"
07
🚀 Push — Enviar para o GitHub
Com as versões salvas localmente, você realiza o push para carregar os seus commits na nuvem do GitHub.
enviar alterações 
# Enviar para o servidor remoto (na branch principal main)
git push origin main

# Nota: Na primeira vez, pode ser necessário usar:
git push --set-upstream origin main
08
📥 Git Clone — Baixar Repositório Existente
Se o projeto já existe no GitHub (criado por você ou por um colega de equipe), você usa o git clone para baixar uma cópia de trabalho idêntica no seu computador.
clonar projeto 
# Clonar o repositório remoto para a sua máquina
git clone https://github.com/usuario/repositorio.git
# Acessar a pasta que foi criada automaticamente
cd repositorio
09
⬇️ Pull — Atualizar e Colaborar
Quando outras pessoas da equipe fazem alterações e enviam para o GitHub, você utiliza o comando git pull para trazer e mesclar essas novidades ao seu código local.
buscar atualizações 
# Puxar atualizações da nuvem para o seu PC
git pull origin main

# Exibir o histórico atualizado de commits
git log --oneline
🔁 O Fluxo Completo em um Bloco

Este é o ciclo essencial que se repete ao longo do desenvolvimento de qualquer software. Configuramos a pasta local, conectamos com a nuvem e mantemos o ciclo de modificação, salvamento local (add/commit) e sincronização (push/pull).

do zero ao deploy remoto 
# 1. Preparar ambiente local
mkdir meu-projeto && cd meu-projeto
git init

# 2. Conectar com o GitHub criado
git remote add origin https://github.com/usuario/meu-projeto.git

# 3. Ciclo de trabalho: salvar mudanças locais
git add .
git commit -m "feat: Setup do projeto"

# 4. Enviar e sincronizar
git push origin main
git pull origin main
💡 Resumindo

O fluxo com Git e GitHub segue sempre a mesma lógica cronológica: estruturar e iniciar seu ambiente, conectar os repositórios, produzir as alterações com segurança através de commits e, por fim, colaborar ativamente por meio de push e pull.

Pode parecer muito comando no começo, mas esse ciclo rapidamente se torna parte natural da rotina de desenvolvimento. Entender esse fluxo é essencial para trabalhar profissionalmente com projetos, equipes e versionamento de código.

Seção 05

Comandos
Essenciais

Dominar o Git não exige decorar centenas de códigos. Na verdade, cerca de 80% do trabalho de um desenvolvedor profissional é feito com apenas alguns comandos fundamentais que garantem a integridade do código.

Dicionário de Sobrevivência

Estes são os comandos que farão parte do seu dia a dia. Eles formam a base para inicializar projetos, salvar seu progresso, navegar pelo histórico e, principalmente, sincronizar seu trabalho com o time através do GitHub.

git init
Inicializar repositório
Cria um repositório Git vazio na pasta atual. Gera a pasta oculta .git/ que rastreia todas as mudanças do projeto.
git clone
Clonar repositório
Baixa uma cópia completa de um repositório remoto (GitHub) para o seu computador, incluindo todo o histórico de commits.
git add
Adicionar ao stage
Prepara arquivos para o próximo commit. Use git add . para todos os arquivos ou git add arquivo.html para um específico.
git commit
Salvar versão
Cria um snapshot do projeto com os arquivos em stage. Sempre use uma mensagem clara: git commit -m "descrição".
git push
Enviar para o GitHub
Envia seus commits locais para o repositório remoto no GitHub. Outros colaboradores poderão ver suas alterações.
git pull
Receber do GitHub
Baixa e integra as alterações feitas por outros colaboradores no repositório remoto para o seu ambiente local.
git status
Ver situação atual
Mostra quais arquivos foram modificados, adicionados ou removidos desde o último commit. Use sempre antes de git add.
git log
Ver histórico
Exibe o histórico de commits do projeto. Use git log --oneline para uma visualização compacta e legível.
git remote -v
Ver repositórios remotos
Mostra quais repositórios do GitHub estão conectados ao projeto local. Muito útil para verificar se o origin foi configurado corretamente.
git branch
Gerenciar branches
Exibe ou cria branches do projeto. A branch principal normalmente se chama main.
git checkout
Trocar versões ou branches
Permite navegar entre branches e versões anteriores do projeto. É muito utilizado em fluxos profissionais mais avançados.
⚙️ Configuração Inicial do Git

Antes de começar a registrar suas alterações, você precisa se identificar para o Git. Isso garante que cada commit tenha o seu nome e e-mail vinculados.

bash — configurar identidade 
# Configure seu nome (aparece nos commits)
git config --global user.name "Seu Nome Aqui"

# Configure seu e-mail (use o mesmo do GitHub!)
git config --global user.email "seu@email.com"

# Verificar a configuração atual
git config --list
⚠️ Importante: O e-mail deve ser exatamente o mesmo cadastrado na sua conta GitHub. Caso contrário, o GitHub não conseguirá atribuir os commits ao seu perfil e você perderá os "quadradinhos verdes" de atividade.
Seção 06

Trabalhando com
Branches

Uma branch (ramificação) é como uma cópia paralela do projeto onde você pode trabalhar em total isolamento, testando ideias e criando recursos sem afetar o código principal que já está funcionando.

A Árvore de Código

Imagine o desenvolvimento de software como o crescimento de uma grande árvore. Compreender esse ecossistema de ramificações é a chave para o verdadeiro trabalho colaborativo em equipe.

🌳 Analogia

O tronco é a branch principal (main) — o código que está em produção, redondo e funcionando. Cada galho é uma branch onde um desenvolvedor trabalha numa nova funcionalidade de forma independente.

Quando o galho está maduro e testado, ele é mesclado de volta ao tronco com um git merge ou através de um Pull Request. Assim, dezenas de desenvolvedores constroem o mesmo app simultaneamente sem gerar caos mútuo. 🌱

Visualizando o Fluxo de Desenvolvimento

Veja abaixo como as linhas de desenvolvimento se separam para a criação de uma funcionalidade e se unem novamente após a aprovação das alterações.

Terminal — Controlando os Ramos

Estes são os comandos práticos para listar, criar, alternar e realizar a fusão histórica das suas ramificações de desenvolvimento.

bash — trabalhando com branches 
# Ver todas as branches locais e identificar onde você está
git branch

# Criar uma nova branch a partir do ponto atual
git branch feature/minha-funcionalidade

# Mudar o seu ambiente para trabalhar na branch desejada
git checkout feature/minha-funcionalidade

# Atalho: Cria e já muda para a nova branch imediatamente
git checkout -b feature/nova

# Para mesclar: vá para a branch que vai receber o código (ex: main) e execute o merge
git checkout main
git merge feature/minha-funcionalidade
Convenções de Nomenclatura no Mercado

Manter as ramificações organizadas por categorias ajuda o time a entender o propósito de cada isolamento de código logo de cara. Veja o padrão profissional:

🌳
main / master
A linha central de produção. Contém o código estável e auditado. Prática padrão: é protegida contra commits diretos, dependendo sempre de aprovações (Code Review).
🌿
feature/nome
Ramificações focadas na construção de novas funcionalidades isoladas. Exemplos: feature/login, feature/checkout-cart.
🐛
fix/nome
Branches cirúrgicas dedicadas exclusivamente à correção de bugs. Exemplos: fix/error-login, fix/broken-button.
🚀
release/versão
Espaço de homologação preparado para consolidações finais de pacotes de entrega estruturados. Exemplo: release/v1.0.0.
💡 Resumindo

Branches permitem trabalhar em funcionalidades separadas sem comprometer o código principal do projeto.

Esse modelo torna possível o trabalho colaborativo em equipes, facilita testes e reduz conflitos durante o desenvolvimento.

Seção 07

Erros ❌
Comuns

Todo desenvolvedor já passou por erros no Git. A diferença entre iniciantes e profissionais não é errar menos — é saber identificar rapidamente o problema e resolver sem pânico.

Problemas do Dia a Dia no Git

Durante o desenvolvimento é normal enfrentar conflitos, commits incorretos, problemas de sincronização e erros de configuração. Entender essas mensagens faz parte da rotina profissional de qualquer desenvolvedor.

❌ git: command not found — Git não instalado
▼

Causa: O Git não está instalado no sistema operacional ou não foi adicionado ao PATH.

Solução:

bash — instalar git 
# Ubuntu / Debian
sudo apt install git

# macOS
brew install git

# Verificar instalação
git --version
💥 Merge conflict — Conflito entre branches
▼

Causa: Dois desenvolvedores alteraram a mesma parte do arquivo em branches diferentes.

Como resolver:

bash + html — resolver conflito 
<<<<<<< HEAD
<h1>Minha versão</h1>

=======

<h1>Versão do colega</h1>

>>>>>>> feature/login

# Resolver manualmente
# Remover os marcadores

git add .

git commit -m "fix: resolve conflito"
💡 O VS Code possui uma interface visual para resolver conflitos sem editar os marcadores manualmente.
🤦 nothing to commit — Esqueceu o git add
▼

Causa: O commit foi executado sem adicionar os arquivos na área de stage.

bash — adicionar antes do commit 
# Verificar alterações
git status

# Adicionar arquivos
git add .

# Criar commit
git commit -m "minha mensagem"
🚫 rejected — Push rejeitado pelo GitHub
▼

Causa: O repositório remoto possui commits que ainda não existem localmente.

bash — sincronizar antes do push 
# Baixar alterações do GitHub
git pull origin main

# Resolver conflitos se necessário

# Enviar novamente
git push origin main
📌 Sempre faça git pull antes de começar a trabalhar e antes de executar um novo git push.
💡 Resumindo

Erros fazem parte do processo de aprendizagem e também da rotina profissional.

Aprender a interpretar mensagens do Git é uma habilidade essencial para trabalhar com versionamento, colaboração e desenvolvimento moderno.

Seção 08

Desafio
Prático

Agora é hora de aplicar na prática os conceitos aprendidos sobre Git, GitHub e versionamento. Você irá criar seu primeiro projeto, conectar ao GitHub e publicar seu código na nuvem como um desenvolvedor profissional.

Seu Primeiro Projeto no GitHub

Nesta atividade, você irá criar um pequeno projeto HTML, inicializar um repositório Git, registrar commits e publicar tudo no GitHub. O objetivo é reproduzir o fluxo real utilizado por desenvolvedores em ambientes profissionais.

🧩 Contexto

Você acabou de entrar em uma equipe de desenvolvimento web e precisa preparar seu ambiente de versionamento. Seu desafio será criar um projeto simples em HTML, versionar os arquivos com Git e publicar tudo no GitHub para que outros desenvolvedores possam acessar e acompanhar suas alterações.

🚀 Comando

Crie um projeto chamado meu-primeiro-site, contendo um arquivo index.html. Inicialize o Git no projeto, faça pelo menos um commit e publique o repositório no GitHub utilizando os comandos aprendidos durante a aula.

⚙️ Fluxo Esperado
bash — fluxo completo do desafio 
# Criar pasta do projeto
mkdir meu-primeiro-site

cd meu-primeiro-site

# Inicializar Git
git init

# Criar arquivo HTML
touch index.html

# Adicionar arquivos
git add .

# Criar commit
git commit -m "feat: cria página inicial"

# Conectar ao GitHub
git remote add origin https://github.com/SEU-USUARIO/meu-primeiro-site.git

# Enviar projeto

📖 Glossário

Os termos técnicos que você vai ouvir todo dia no mundo do Git e GitHub.

Repository (Repo)
A pasta do projeto gerenciada pelo Git. Contém todos os arquivos, histórico de versões e configurações. Pode ser local (no seu PC) ou remoto (no GitHub).
Commit
Um snapshot (foto) do estado do projeto em um momento específico. Cada commit tem um ID único, um autor, uma data e uma mensagem descritiva.
Push
Enviar commits locais para o repositório remoto (GitHub). É o "upload" do seu trabalho para a nuvem.
Pull
Baixar e integrar commits do repositório remoto para o local. É o "download + merge" das alterações do time.
Branch
Uma ramificação independente do código. Permite desenvolver funcionalidades em paralelo sem afetar a branch principal (main).
Merge
Unir duas branches. Os commits de uma branch são integrados à outra. Se houver edições no mesmo ponto, ocorre um "merge conflict" que precisa ser resolvido manualmente.
Clone
Cópia completa de um repositório remoto para o computador local, incluindo todo o histórico de commits e branches.
Pull Request (PR)
Pedido para integrar uma branch ao código principal. Permite revisão de código por outros membros da equipe antes do merge.
Stage / Index
Área intermediária entre os arquivos modificados e o commit. Você escolhe quais mudanças incluir no próximo commit com git add.
Remote
Repositório hospedado em um servidor (ex: GitHub). O nome padrão do remote principal é origin.
