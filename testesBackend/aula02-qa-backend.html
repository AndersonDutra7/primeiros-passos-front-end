Seção 01

Modelagem de Cenários Complexos

Um bom engenheiro de QA não testa apenas o caminho feliz. Ele modela todos os mundos possíveis que um requisito pode enfrentar.

Todo requisito possui pelo menos três famílias de cenários que precisam ser cobertos: o caminho feliz (Sucesso), os desvios esperados (Exceção) e as fronteiras extremas do comportamento (Limites).

As três famílias de cenários

S
Cenários de Sucesso (Happy Path)
O sistema recebe dados válidos e executa o fluxo principal conforme especificado. O resultado esperado é sempre o comportamento descrito como "correto" nos requisitos.
Exemplo

Requisito: "O CPF deve conter exatamente 11 dígitos numéricos."
Cenário de Sucesso: Enviar CPF = 12345678901 → Sistema aceita e continua o fluxo.

E
Cenários de Exceção (Sad Path)
O sistema recebe dados inválidos, ausentes ou inesperados. O objetivo é verificar se o sistema trata o erro de forma elegante — retornando mensagens claras, status HTTP corretos e nunca quebrando.
Exemplo

Requisito: "O CPF deve conter exatamente 11 dígitos numéricos."
Cenários de Exceção: CPF vazio → 400 Bad Request. CPF com letras → 400 Bad Request. CPF nulo (null) → 400 Bad Request.

L
Cenários de Limite (Edge Cases)
O sistema está na fronteira entre válido e inválido. Esses casos testam as exatas bordas da especificação — o mínimo, o máximo, o exato limite e um passo além dele.
Exemplo — Análise do Valor Limite (AVL)

Requisito: "O ISBN deve ter exatamente 13 dígitos."
Limite −1: 12 dígitos → deve rejeitar
Limite exato: 13 dígitos → deve aceitar
Limite +1: 14 dígitos → deve rejeitar

💡
Regra de ouro: Para cada requisito de validação, aplique sempre as três famílias. Um requisito que aceita apenas cenários de sucesso está 85% não-testado. As falhas em produção quase sempre vivem nos cenários de exceção e limite.

A técnica do E SE...

A ferramenta mental mais poderosa do QA é fazer perguntas do tipo "E se..." sobre cada requisito. Esse exercício força a imaginação além do caminho óbvio.

Requisito E se... (cenário derivado) Família Resultado Esperado
CPF deve ter 11 dígitos O CPF vier completamente vazio? Exceção 400 — "CPF é obrigatório"
CPF deve ter 11 dígitos O CPF tiver caracteres especiais (!@#)? Exceção 400 — "CPF deve conter apenas dígitos"
CPF deve ter 11 dígitos O CPF tiver exatamente 11 dígitos válidos? Sucesso 200/201 — Operação realizada
CPF deve ter 11 dígitos O CPF tiver 10 dígitos (limite −1)? Limite 400 — "CPF deve ter 11 dígitos"
CPF deve ter 11 dígitos O CPF tiver 12 dígitos (limite +1)? Limite 400 — "CPF deve ter 11 dígitos"
CPF deve ter 11 dígitos O CPF for null no JSON? Exceção 400 — "CPF não pode ser nulo"
Seção 02

Matriz de Classificação

Além das famílias de cenários, cada caso de teste pertence a uma ou mais dimensões de qualidade do software. Classificar corretamente determina quem revisa, qual criticidade o defeito recebe e onde ele deve ser investigado.

⚙️
Funcional
Lógica de Negócio
Testa se o sistema executa corretamente as regras de negócio especificadas. O foco é no o que o sistema faz.
  • O saldo negativo gera alerta?
  • O cadastro com dados válidos retorna 201?
  • A meta com valor zero é bloqueada?
  • A devolução do livro atualiza o status?
🔒
Segurança
Autorização e Proteção de Dados
Testa se o sistema protege dados sensíveis e impede acessos não autorizados. O foco é no quem pode fazer o quê.
  • Usuário sem admin pode excluir?
  • Token expirado ainda concede acesso?
  • Injeção de SQL no campo de busca?
  • Dados de outro usuário acessíveis?
🔍
Validação
Integridade de Entrada
Testa se o sistema rejeita dados inválidos com mensagens claras e precisas. O foco é na entrada de dados e no feedback ao consumidor da API.
  • Campo obrigatório ausente retorna 400?
  • Tipo errado (string no lugar de número)?
  • Mensagem de erro é descritiva?
  • ISBN com 12 dígitos é rejeitado?
🖥️
Usabilidade da API
Contrato e Consistência
Testa se a API segue seu contrato de forma consistente — status HTTP corretos, estrutura de resposta previsível, mensagens padronizadas.
  • Criação usa 201 (não 200)?
  • Corpo de erro segue estrutura padrão?
  • Recurso não encontrado usa 404?
  • Campos de data têm formato ISO 8601?
⚠️
Um caso de teste pode ter mais de uma dimensão. Exemplo: testar se um usuário sem permissão recebe 403 Forbidden (e não 200) é ao mesmo tempo Segurança e Usabilidade da API. Use a dimensão principal como a "âncora" na sua tabela.

Mapeando as dimensões nos projetos dos grupos

Dimensão Exemplo — Gestão Financeira (Squad Delta) Exemplo — Biblioteca (Squad Echo)
Funcional Despesa futura deve ser bloqueada pelo sistema Usuário com 3 livros não pode fazer novo empréstimo
Segurança Usuário A não pode ver lançamentos do Usuário B Admin pode excluir acervo; usuário comum não
Validação Lançamento com valor 0 retorna 400 com mensagem clara ISBN com 12 dígitos retorna 400 — "ISBN deve ter 13 dígitos"
Usabilidade Novo lançamento criado retorna 201, não 200 Busca com menos de 3 chars retorna 400 — contrato claro
Seção 03

Anatomia de um Caso de Teste

Um caso de teste bem escrito é um documento de comunicação. Qualquer pessoa da equipe — dev, outro QA, o cliente — deve conseguir reproduzir o teste apenas lendo-o.

🧑‍🍳 Analogia

Pense no caso de teste como uma receita culinária. Uma receita ruim diz "adicione sal a gosto". Uma receita profissional diz "adicione 5g de sal refinado antes de ferver". A ambiguidade em QA custa tempo e gera retrabalho.

Os 8 campos obrigatórios

01
ID do Caso de Teste
Identificador único rastreável. Convenção: CT-[projeto]-[número]. Ex: CT-FIN-001, CT-LIB-001. Permite referenciar o caso em relatórios de bug sem ambiguidade.
02
Requisito Vinculado
O ID do requisito ou regra de negócio que originou este caso. Garante a rastreabilidade — se o requisito mudar, todos os casos vinculados precisam ser revistos.
03
Título / Descrição
Frase objetiva que descreve o que está sendo testado. Ex: "Rejeitar cadastro de despesa com data futura". O título deve ser autoexplicativo sem precisar abrir o caso.
04
Pré-condições
Estado do sistema antes do teste. Ex: "Usuário autenticado com token válido", "Banco de dados limpo", "Categoria 'Alimentação' já cadastrada". Sem pré-condições claras, o teste pode falhar por razões erradas.
05
Dados de Entrada
Os valores exatos usados na requisição. Nunca use "dados genéricos" — especifique: { "valor": 0.00, "categoria_id": null, "data": "2027-01-01" }. A precisão nos dados é o que torna o teste reproduzível.
06
Passos de Execução
Sequência numerada e precisa de ações. Ex: "1. Autenticar via POST /auth/login. 2. Copiar o token da resposta. 3. Enviar POST /lancamentos com o body abaixo e o token no header Authorization."
07
Resultado Esperado
O comportamento exato que o sistema deve apresentar. Inclua: status HTTP, estrutura do corpo de resposta, mensagem de erro esperada, e qualquer efeito no banco de dados. Ex: HTTP 400 com body { "erro": "Data de despesa não pode ser futura" }.
08
Dimensão + Família de Cenário
A classificação do caso: qual dimensão (Funcional / Segurança / Validação / Usabilidade) e qual família (Sucesso / Exceção / Limite). Essencial para gerar métricas de cobertura e priorizar execução.

Exemplo completo de Caso de Teste

CT-FIN-003 — Caso de Teste Completo
ID:              CT-FIN-003
Requisito:       RN-02 — Restrição Temporal de Lançamentos
Título:          Rejeitar cadastro de despesa com data futura
Dimensão:        Funcional
Família:         Exceção
Prioridade:      Alta

── Pré-condições ─────────────────────────────────────────
✓ Usuário autenticado com JWT válido (não expirado)
✓ Categoria "Alimentação" (id: 1) já existe no banco
✓ Data atual do servidor: 2026-06-01

── Dados de Entrada ──────────────────────────────────────
POST /api/lancamentos
{
  "tipo":         "DESPESA",
  "valor":        150.00,
  "categoria_id": 1,
  "data":         "2026-12-31"   // data futura
}

── Passos de Execução ────────────────────────────────────
1. Autenticar via POST /api/auth/login com credenciais válidas
2. Copiar o token do campo access_token da resposta
3. Adicionar header Authorization: Bearer {token}
4. Enviar POST /api/lancamentos com o body acima

── Resultado Esperado ────────────────────────────────────
HTTP 400 Bad Request
{
  "erro": "Despesas não podem ter data futura",
  "campo": "data"
}
Nenhum registro criado no banco de dados.
🚨
Erro mais comum dos iniciantes: escrever o resultado esperado como "o sistema deve dar erro". Isso não é resultado esperado — é wishful thinking. Sempre especifique o status HTTP exato e a mensagem de erro exata. O que não é mensurável não é testável.
Seção 04

Técnicas de Derivação de Cenários

Existem técnicas formais para derivar casos de teste de forma sistemática — garantindo cobertura máxima com o mínimo de redundância.

📏
Análise do Valor Limite (AVL)
Para qualquer campo com restrição numérica, teste: mínimo −1, mínimo exato, máximo exato e máximo +1. Exemplo: campo que aceita 1 a 100 → testar com 0, 1, 100 e 101. Elimina a falácia de "o erro só ocorre nos extremos".
🗂️
Partição de Equivalência (PE)
Agrupe entradas em classes onde o sistema se comporta identicamente. Em vez de testar todos os CPFs inválidos, teste um representante de cada classe: vazio, muito curto, muito longo, com letras, com especiais. Reduz casos redundantes.
📊
Tabela de Decisão
Quando múltiplas condições se combinam para determinar o resultado, mapeie todas as combinações possíveis. Essencial para regras do tipo "se A e B então X, se A e não-B então Y". Evita caminhos lógicos esquecidos.
🔄
Transição de Estado
Para entidades que mudam de estado (ex: Livro: Disponível → Emprestado → Devolvido), mapeie cada transição válida e cada transição inválida. Teste o que pode acontecer em cada estado e o que não deve ser permitido.

🔥 Entrega Parcial — Aula 02

Tabelas de Casos de Teste — v1.0

Com base nas regras de negócio identificadas no Plano de QA, cada grupo deve derivar, classificar e escrever os casos de teste do seu projeto usando as técnicas aprendidas nesta aula.

A entrega deve cobrir todas as regras de negócio listadas no projeto, com pelo menos um caso de Sucesso, um de Exceção e um de Limite para cada regra (onde aplicável). O documento deve ser entregue em formato PDF.

🆔
1. IDs e Rastreabilidade
Cada caso de teste deve ter um ID único no padrão CT-[PROJETO]-[NNN] e estar vinculado ao ID do requisito de origem da Aula 01.
🗺️
2. Cobertura das 3 Famílias
Para cada regra de negócio, derivar cenários de Sucesso, Exceção e Limite. Usar as técnicas de AVL e Partição de Equivalência onde aplicável.
🧩
3. Classificação por Dimensão
Cada caso deve estar classificado em uma das 4 dimensões: Funcional, Segurança, Validação ou Usabilidade da API. Use a coluna "Dimensão" na tabela.
🎯
4. Resultado Esperado Preciso
Nenhum resultado pode ser vago. Deve conter: status HTTP, estrutura da resposta esperada, e mensagem de erro (quando aplicável). "Deve dar erro" não é aceito.
📋
Estrutura mínima da tabela: ID | Requisito Vinculado | Título do Cenário | Família (S/E/L) | Dimensão | Dados de Entrada | Resultado Esperado | Status (Não Executado)

Seção 06 — Momento Crítico

A Sabatina do Lead QA

Em empresas reais, o Lead de QA revisa os casos de teste da equipe e faz perguntas de estresse — aquelas que expõem buracos na cobertura e no raciocínio. Agora é a sua vez de responder.

🔥 Teste de Estresse — Lead QA em ação

Suas tabelas estão prontas. Estou revisando agora.

Para cada pergunta abaixo, pense: o seu caso de teste cobre esse cenário? Você tem o resultado esperado documentado com precisão? Se a resposta for "não sei" ou "talvez", você precisa revisar sua tabela.

🤔
"E se o CPF vier completamente vazio no body da requisição?" — Qual o status HTTP que o sistema deve retornar? A mensagem de erro é específica para "vazio" ou genérica demais?
🤔
"Como a lógica reage se eu enviar um caractere especial no campo de CPF? E o que acontece com uma tag HTML <script>alert(1)</script>?" — Você testou XSS básico? Isso está classificado como Segurança na sua tabela?
🤔
"O que acontece se eu tentar criar dois livros com o mesmo ISBN?" — A regra de unicidade está coberta? Qual status é retornado: 400 ou 409? Isso está documentado?
🤔
"Se o usuário tem exatamente 3 livros emprestados e tenta pegar o 4º, o sistema bloqueia com 400 ou 422? A mensagem diz qual é o limite?" — Você testou exatamente no limite (3) e um acima (4)?
🤔
"E se alguém tentar registrar uma despesa com valor -100? O sistema aceita? Qual o comportamento com 0?" — Você usou Análise do Valor Limite aqui? Zero é tratado como caso especial?
🤔
"Um usuário comum consegue ver os dados financeiros de outro usuário se souber o ID dele?" — Você tem um caso de teste de isolamento de dados na dimensão Segurança?
🤔
"O que acontece se eu enviar o campo data como string "ontem" em vez de uma data ISO válida?" — Tipo de dado inválido está coberto na sua partição de equivalência?
🤔
"Quando você cria um recurso com sucesso, o sistema retorna 200 ou 201? É consistente em todos os endpoints?" — Você testou a Usabilidade da API além da lógica funcional?
💡
Como se preparar para a sabatina: Após escrever cada caso de teste, pergunte a si mesmo: "O que mais pode dar errado aqui?" e "Meu resultado esperado é específico o suficiente para ser verificável?". Se houver qualquer ambiguidade, o caso precisa ser reescrito.
Glossário

Termos da Aula 02

Happy Path
Cenário de teste onde todos os dados são válidos e o fluxo principal é executado sem desvios. Também chamado de "caminho feliz" ou Cenário de Sucesso.
Sad Path
Cenário de teste onde dados inválidos, ausentes ou inesperados são fornecidos. O objetivo é validar o tratamento de erros do sistema.
Edge Case
Cenário que testa exatamente as bordas de uma especificação — o valor mínimo, o máximo, e um passo além de cada limite. Em português: Caso de Limite.
AVL
Análise do Valor Limite — técnica que sistematicamente testa o ponto imediatamente abaixo, exatamente no, e imediatamente acima de cada limite numérico de uma especificação.
Partição de Equivalência
Técnica de agrupamento de entradas em classes onde o sistema se comporta identicamente — permitindo testar um representante de cada classe em vez de todos os valores possíveis.
Rastreabilidade
Capacidade de vincular cada caso de teste ao requisito que o originou. Garante que mudanças nos requisitos sejam refletidas nos casos de teste correspondentes.
Pré-condição
Estado exato que o sistema deve estar antes da execução do caso de teste. Sem pré-condições bem definidas, um caso pode falhar por razões não relacionadas ao que está sendo testado.
Dimensão de Teste
Categoria de qualidade que o caso de teste valida: Funcional (lógica de negócio), Segurança (acesso e proteção), Validação (integridade de entrada) ou Usabilidade da API (contrato).
