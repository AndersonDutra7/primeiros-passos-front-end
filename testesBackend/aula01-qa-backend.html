Seção 01

O que é QA?

QA — Quality Assurance — não é só "achar bugs". É uma mentalidade que permeia todo o ciclo de desenvolvimento: planejar, verificar, validar e garantir que o sistema entregue o que o usuário espera.

QA não é só testar

Muita gente confunde QA com "a pessoa que clica no sistema procurando erros". Na realidade, QA — Quality Assurance (Garantia de Qualidade) — é um processo mais amplo que envolve prevenção de falhas desde o início do projeto, não apenas a detecção delas no final.

Enquanto o desenvolvedor pergunta "isso funciona?", o profissional de QA pergunta "isso funciona do jeito que o usuário espera, em todos os cenários possíveis, incluindo os que ninguém pensou?".

🏥 Analogia

Imagine um hospital que só verifica se os medicamentos estão corretos depois que o paciente os tomou. Absurdo, certo? O QA é o processo que garante que tudo seja checado antes de chegar ao paciente — o usuário final.

No software, o "paciente" é o usuário. O QA protege ele de "remédios errados" — sistemas com bugs, dados corrompidos, regras de negócio violadas.

As três perguntas do QA

Verificação
Estamos construindo certo?
O sistema está sendo construído de acordo com as especificações técnicas e os requisitos definidos?
Validação
Construímos a coisa certa?
O sistema atende à necessidade real do usuário? O que foi pedido resolve o problema de verdade?
Prevenção
Como evitar erros futuros?
Quais processos e padrões podemos adotar para que esses problemas não se repitam em próximas entregas?

Por que QA importa?

💸
Custo de correção aumenta
Um bug encontrado em desenvolvimento custa 10x menos para corrigir do que um bug encontrado em produção. Em alguns setores, como saúde e finanças, o custo pode ser irreversível.
📉
Reputação em jogo
Sistemas que falham em produção geram cancelamentos, processos judiciais e perda de confiança. Um único incidente pode destruir anos de credibilidade construída.
🔒
Segurança e conformidade
Muitos sistemas precisam estar em conformidade com leis como a LGPD. Falhas de QA podem resultar em vazamentos de dados e multas milionárias.
🤝
Confiança do cliente
Um produto bem testado é entregue com previsibilidade. O cliente sabe o que esperar, os prazos são cumpridos e a equipe ganha credibilidade no mercado.
Seção 02

O que é Homologação?

Antes de qualquer software chegar ao usuário real, ele passa por um ambiente controlado onde é testado exaustivamente. Esse ambiente é chamado de Homologação — e é onde o QA vive.

Ambientes de Software

Todo projeto de software minimamente organizado possui pelo menos três ambientes separados. Cada um tem um propósito específico e não devem se misturar.

Ambiente Quem usa Propósito Dados
Desenvolvimento (DEV) Desenvolvedor Escrever e testar código novo Fictícios / locais
Homologação (HML) QA / Cliente / PO Validar antes de ir ao ar Cópia mascarada do real
Produção (PROD) Usuário final Sistema real em operação Dados reais dos clientes
💡 Homologação é o portão de segurança. É a última barreira antes do usuário real. O trabalho de vocês neste projeto será 100% em homologação — garantindo que os sistemas simulados estejam prontos e confiáveis.

O que acontece durante a homologação?

1
Recebimento dos Requisitos
O time de QA recebe o documento de requisitos — funcionalidades e regras de negócio — e estuda o que o sistema deve fazer.
2
Planejamento dos Testes
Com base nos requisitos, o time cria os casos de teste — cenários que cobrem tanto os fluxos esperados quanto os inesperados.
3
Execução dos Testes
Cada caso de teste é executado manualmente ou automaticamente. Os resultados são registrados: passou ✅ ou falhou ❌.
4
Reporte de Defeitos
Todo comportamento incorreto é registrado como um defeito (bug), com passos para reprodução, severidade e evidências.
5
Aprovação ou Reprovação
Com base nos resultados, o sistema é aprovado para produção ou reprovado para correção. Essa decisão é documentada no Comitê de Aprovação.
Seção 03

O que é um Caso de Teste?

Um caso de teste é um roteiro documentado que descreve exatamente como testar uma funcionalidade — o que fazer, quais dados usar e qual resultado é esperado.

Anatomia de um caso de teste

Todo caso de teste bem escrito responde a seis perguntas fundamentais:

Campo O que descreve Exemplo prático
ID Identificador único do caso CT-001
Título Nome curto e descritivo Cadastro com e-mail duplicado
Pré-condição O que deve existir antes de executar Usuário joao@email.com já cadastrado
Passos O que fazer, passo a passo 1. Acessar /cadastro 2. Preencher joao@email.com 3. Clicar em Salvar
Resultado Esperado O que o sistema deve fazer Exibir erro "E-mail já cadastrado"
Resultado Obtido O que o sistema realmente fez Preenchido após execução

Tipos de cenário

Um bom QA não testa apenas o "caminho feliz" — ele pensa em tudo que pode dar errado.

✅ Fluxo Positivo (Happy Path)
→ Cadastro com todos os dados válidos
→ Login com usuário e senha corretos
→ Alteração bem-sucedida de dados
→ Exclusão com permissão de administrador
❌ Fluxo Negativo (Sad Path)
→ Cadastro com e-mail já existente
→ Login com senha incorreta
→ Exclusão sem permissão de administrador
→ Senha com menos de 6 caracteres
⚠️ Regra de ouro: para cada regra de negócio do sistema, deve existir pelo menos um caso de teste positivo (regra respeitada) e um negativo (regra violada). Se o sistema tem 10 regras, você tem no mínimo 20 casos de teste para escrever.
Seção 04

O que é um Defeito?

Um defeito (ou bug) é qualquer divergência entre o comportamento esperado e o comportamento real do sistema. Nem toda coisa estranha é um defeito — precisa ser documentado, classificado e reproduzível.

A diferença entre erro, defeito e falha

Erro
Ação humana
O desenvolvedor digitou algo errado ou interpretou mal o requisito. É a causa — acontece na cabeça ou na digitação do programador.
Defeito
Problema no código
O resultado do erro humano no código — uma linha errada, uma condição invertida, uma validação ausente. É o problema documentado.
Falha
Manifestação em execução
Quando o defeito é ativado e o sistema se comporta incorretamente na frente do usuário. É o sintoma visível do defeito.

Classificação por Severidade

Nem todo bug é uma emergência. A severidade define o impacto do defeito no sistema:

Nível Nome Descrição Exemplo
🔴 S1 Crítico Sistema inacessível ou dados corrompidos Nenhum usuário consegue fazer login
🟡 S2 Alto Funcionalidade principal quebrada, sem contorno CPF aceita menos de 11 dígitos
🟣 S3 Médio Funcionalidade impactada, mas existe contorno Mensagem de erro com texto errado
⚪ S4 Baixo Cosmético, usabilidade, sem impacto funcional Botão com cor levemente diferente do design
✍️ Como documentar um defeito

Um defeito precisa ser reproduzível e claro. O desenvolvedor que vai corrigir não estava lá quando você encontrou o problema — ele precisa conseguir reproduzir seguindo o seu relato. Use sempre: Título + Passos para Reprodução + Resultado Esperado + Resultado Obtido + Severidade + Evidência (print ou vídeo).

Seção 05 — Entrega do Desafio

Documentos de Requisitos

Cada grupo receberá um sistema diferente para homologar ao longo das 4 aulas. Leiam com atenção — vocês serão os responsáveis por garantir a qualidade dessas aplicações.

👥 A organização técnica será distribuída no formato de 5 Squads de Engenharia de QA (compostas por 3 integrantes, com ajustes operacionais validados pela coordenação). A alocação dos escopos de negócio será realizada por meio de um processo de Distribuição Oficial e direcionada, onde cada time assumirá a responsabilidade integral pelo ciclo de vida de testes de uma das soluções mapeadas a seguir.
Projeto 01 — Squad Alpha
Sistema de Gerenciamento de Usuários e Perfis
Plataforma corporativa de administração de contas com controle de acesso distribuído e níveis de permissão por perfil.
  • Cadastro de novos usuários (Autogestão)
  • Login com autenticação e recuperação de acesso
  • Painel de alteração de dados do perfil
  • Módulo de moderação e exclusão de contas
    • Regras de Negócio
    • Unicidade de Identidade: O e-mail informado deve ser único no sistema. Não é permitido o cadastro de dois usuários com o mesmo e-mail.
    • Formato do CPF: O campo CPF é obrigatório e deve possuir exatamente 11 dígitos numéricos, rejeitando letras ou contagens menores/maiores.
    • Política de Senhas: A senha deve possuir no mínimo 6 caracteres. O sistema deve validar a confirmação da senha no momento do cadastro.
    • Hierarquia de Perfis (Acesso): Existem três perfis no sistema: Comum, Moderador e Administrador.
    • Regra de Alteração: Usuários do perfil Comum só podem alterar seus próprios dados de perfil (Nome e Senha). Eles não podem alterar seu próprio nível de acesso.
    • Regra de Exclusão: Usuários do perfil Comum e Moderador não possuem permissão para excluir contas. Apenas usuários com perfil Administrador visualizam e executam a exclusão de usuários.
    • Bloqueio Preventivo: O sistema deve exibir uma mensagem de erro clara e impedir o acesso após 3 tentativas consecutivas de login com senha incorreta.
    Projeto 02 — Squad Beta
    Sistema de Agendamento de Consultas Médicas
    Plataforma clínica de marcação de consultas entre pacientes e profissionais de saúde com gestão de agenda integrada.
  • Cadastro de pacientes e médicos
  • Listagem dinâmica de horários e especialidades disponíveis
  • Agendamento e confirmação de consultas
  • Módulo de cancelamento e remanejamento de horários
    • Regras de Negócio
    • Validação de Identidade (CPF): O paciente deve obrigatoriamente possuir um CPF válido com exatamente 11 dígitos numéricos para efetivar o cadastro na plataforma.
    • Antecedência Mínima de Agendamento: Uma nova consulta só pode ser agendada se houver uma antecedência mínima de 24 horas em relação ao horário atual do sistema.
    • Concorrência de Agenda (Médico): O sistema deve impedir que um mesmo médico possua dois agendamentos confirmados no mesmo dia e horário.
    • Bloqueio de Choque de Horários (Paciente): Um paciente não pode agendar duas consultas diferentes para o mesmo horário, mesmo que sejam com médicos de especialidades distintas.
    • Política de Cancelamento Justo: O paciente pode realizar o cancelamento da consulta diretamente pelo sistema apenas com, no mínimo, 2 horas de antecedência do horário marcado.
    • Limite de Agendamentos Ativos: Para evitar fraudes ou ausências em massa, cada paciente cadastrado pode ter no máximo 3 consultas agendadas de forma futura e simultânea no sistema.
    • Restrição de Especialidades: Um médico só pode ter horários disponibilizados e vinculados à especialidade médica (CRM válido) previamente cadastrada em seu perfil técnico.
    Projeto 03 — Squad Charlie
    Sistema de Controle de Estoque e Inventário
    Plataforma logística de gestão de produtos em depósito com controle de movimentações transacionais e gatilhos de reposição automatizados.
  • Cadastro e categorização de produtos
  • Módulo de movimentação (Registrar Entrada e Saída)
  • Painel de emissão de relatórios de inventário
  • Sistema de alertas de estoque crítico e reposição
    • Regras de Negócio
    • Identificação Única (SKU): Cada produto deve possuir um código identificador único (SKU) no sistema. Não será permitido o cadastro de dois produtos com o mesmo código.
    • Validação de Valores Quantitativos: O campo de quantidade do produto, tanto no cadastro inicial quanto nas atualizações, nunca poderá receber valores negativos ou nulos.
    • Limite Transacional de Saída: O sistema deve bloquear qualquer operação de saída (venda ou baixa) cuja quantidade informada exceda o volume atualmente disponível no estoque físico.
    • Gatilho Automático de Alerta Mínimo: O sistema deve disparar um status visual de alerta ("Estoque Crítico") assim que a quantidade de um item atingir um volume menor que 10 unidades.
    • Histórico de Log Transacional: Toda entrada ou saída de produto deve obrigatoriamente registrar de forma imutável a data, o horário, a quantidade movimentada e o ID do usuário que realizou a operação.
    • Preço de Venda vs. Custo: No cadastro ou alteração de dados do produto, o sistema deve emitir uma trava impedindo que o preço de venda seja igual ou inferior ao preço de custo do item.
    • Bloqueio de Inativação de Itens: O sistema não deve permitir a desativação ou exclusão lógica de um produto no catálogo caso ele ainda possua saldo em estoque maior do que zero.
    Projeto 04 — Squad Delta
    Sistema de Gestão Financeira Pessoal
    Aplicação financeira para controle transacional de receitas, despesas, planejamento orçamentário e acompanhamento de metas de economia.
  • Cadastro de lançamentos (Receitas e Despesas)
  • Categorização de movimentações e tags
  • Dashboard consolidado de saldo e resumo mensal
  • Módulo de definição e progresso de metas financeiras
    • Regras de Negócio
    • Consistência de Valores monetários: Todo e qualquer lançamento registrado (seja receita ou despesa) deve, obrigatoriamente, possuir um valor numérico estritamente maior do que zero.
    • Restrição Temporal de Lançamentos: O sistema deve impedir o registro de despesas com datas futuras em relação ao horário atual do servidor. Receitas futuras são permitidas (previsão).
    • Vínculo de Categorização Obrigatória: Nenhuma movimentação financeira pode ser salva sem estar associada a uma categoria válida previamente existente (ex: Alimentação, Transporte, Salário).
    • Critérios de Criação de Metas: O módulo de metas de economia exige que o usuário defina obrigatoriamente um valor-alvo maior que zero e uma data de prazo final válida (data futura).
    • Gatilho de Notificação de Limite da Meta: O sistema deve disparar um alerta visual automático no painel do usuário caso as despesas de uma categoria atinjam 80% do teto orçamentário definido para ela.
    • Regra de Alerta de Saldo Negativo: Caso uma nova despesa faça o saldo total consolidado da conta transicionar para um valor abaixo de zero, o sistema deve processar a operação, mas emitir um alerta imediato de "Saldo Negativo".
    • Impedimento de Exclusão Histórica: O sistema não deve permitir a exclusão de categorias personalizadas que possuam lançamentos financeiros vinculados a ela no histórico do mês atual.
    Projeto 05 — Squad Echo
    Sistema de Biblioteca Digital e Acervo
    Plataforma de gestão de acervo literário, controle transacional de empréstimos, devoluções e rastreamento de pendências para instituições de ensino.
  • Cadastro de títulos e catalogação de acervo
  • Módulo de busca avançada (por título, autor e ISBN)
  • Fluxo de solicitação de empréstimo e registro de devolução
  • Painel de histórico e extrato de pendências por usuário
    • Regras de Negócio
    • Padrão Internacional do Acervo (ISBN): Todo livro cadastrado deve possuir um código ISBN obrigatório contendo exatamente 13 dígitos numéricos (padrão ISBN-13).
    • Teto Limite de Empréstimos Ativos: Um mesmo usuário não pode possuir mais de 3 livros emprestados simultaneamente de forma ativa no sistema.
    • Prazo Regulamentar de Devolução: O período máximo fixado para a posse e devolução de qualquer livro emprestado é de exatamente 14 dias corridos.
    • Bloqueio por Inadimplência / Atraso: O sistema deve impedir novos empréstimos para qualquer usuário que possua pelo menos um livro com o prazo de devolução vencido.
    • Trava de Disponibilidade de Exemplar: Um livro físico ou exemplar digital específico cujo status atual conste como "Emprestado" não pode ser alocado para outro usuário até que sua devolução seja processada.
    • Critério Mínimo de Busca Avançada: O mecanismo de pesquisa deve exigir que o usuário digite pelo menos 3 caracteres no campo de busca para disparar a filtragem por título ou autor.
    • Abono de Devolução no Mesmo Dia: O sistema deve permitir que um livro seja retirado e devolvido no mesmo dia de calendário, registrando a movimentação no histórico sem gerar penalidades ou erros de concorrência de datas.

    🔥 Entrega Parcial — Aula 01

    Plano de QA — Versão Inicial

    A partir da análise do documento de requisitos, cada equipe devra produzir a primeira entrega oficial do projeto: o Plano de QA.

    Este documento servirá como base para as próximas etapas do ciclo de testes, registrando os objetivos, requisitos identificados, escopo, estratégia, riscos e critérios de aprovação do sistema.

    O trabalho deverá ser entregue exclusivamente em formato PDF, contemplando todos os itens obrigatórios apresentados a seguir.

    🎯
    1. Objetivos do Teste
    Definam pelo menos 10 objetivos de teste com base nos requisitos e riscos identificados.
    📋
    2. Requisitos Identificados
    Liste todos os requisitos funcionais e regras de negócio encontrados no documento do projeto.
    🗺️
    3. Escopo
    Defina claramente o que será testado (In Scope) e o que ficará fora deste ciclo (Out of Scope).
    ⚙️
    4. Estratégia de Teste
    Descreva a abordagem utilizada, técnicas de teste, prioridades e divisão da equipe.
    ⚠️
    5. Riscos Identificados
    Relacione os principais riscos de negócio e seus impactos caso ocorram em produção.
    ✅
    6. Critérios de Aprovação
    Defina quais condições devem ser atendidas para considerar o sistema apto para homologação.

    O que colocar em cada seção?

    🎯 Objetivos do Teste — Como escrever
    ▼

    Os objetivos devem responder: "O que precisamos validar para reduzir os riscos do projeto?"

    O plano deve conter no mínimo 10 objetivos de teste, distribuídos entre as funcionalidades e regras de negócio identificadas.

    Exemplos de bons objetivos:

    • Garantir que as regras de negócio do cadastro sejam respeitadas.
    • Verificar que usuários sem permissão não consigam executar ações restritas.
    • Assegurar que dados inválidos sejam rejeitados pelo sistema.
    • Validar que o processo de autenticação funcione corretamente.
    • Confirmar que o sistema se comporte adequadamente nos limites de cada regra de negócio.

    Dica: evite objetivos genéricos como "testar o sistema". Seja específico sobre o que precisa ser validado.

    📋 Requisitos Identificados
    ▼

    Antes de planejar os testes, a equipe deve identificar todas as funcionalidades e regras de negócio descritas no documento de requisitos.

    Exemplo:

    • RF01 — Cadastro de usuários
    • RF02 — Login
    • RF03 — Alteração de dados
    • RF04 — Exclusão de registros
    • RN01 — E-mail deve ser único
    • RN02 — Senha mínima de 6 caracteres

    Essa lista servirá como base para os objetivos, riscos e futuros casos de teste.

    🗺️ Escopo — O que será e não será testado
    ▼

    O escopo define exatamente quais funcionalidades e regras serão avaliadas neste ciclo de testes.

    In Scope (será testado): funcionalidades, fluxos e regras de negócio descritas nos requisitos.

    Out of Scope (não será testado): aspectos que não fazem parte dos objetivos antigos do projeto, como testes de carga, performance, segurança avançada ou integrações não previstas.

    Definir claramente o escopo evita interpretações equivocadas sobre o que faz ou não parte do trabalho da equipe.

    ⚙️ Estratégia de Teste
    ▼

    A estratégia descreve como a equipe pretende conduzir as atividades de teste.

    Inclua na estratégia:

    • Técnica principal: Caixa-Preta.
    • Abordagem: Partição por Equivalência e Análise de Valor Limite.
    • Prioridade: definir quais funcionalidades possuem maior criticidade.
    • Distribuição: dividir responsabilidades entre os integrantes da equipe.
    ⚠️ Riscos Identificados
    ▼

    Todo plano de QA deve registrar os principais riscos do sistema e o impacto que eles podem causar caso cheguem à produção.

    Exemplos:

    • Usuários comuns conseguirem acessar funções administrativas.
    • E-mails duplicados serem aceitos pelo sistema.
    • Dados inválidos serem armazenados.
    • Falhas no processo de autenticação.
    • Regras de negócio não serem aplicadas corretamente.

    Classifique cada risco como Baixo, Médio, Alto ou Crítico.

    ✅ Critérios de Aprovação
    ▼

    Os critérios de aprovação definem quando o sistema poderá ser considerado apto para avançar para a próxima etapa do processo de testes.

    Exemplos:

    • Todas as funcionalidades principais foram analisadas.
    • As regras de negócio foram validadas.
    • Não existem defeitos críticos conhecidos.
    • Os objetivos definidos no plano foram atendidos.
    • Os riscos mais importantes foram considerados pela equipe.

    6. Critérios de Aprovação (Exit Criteria)

    Conjunto de condições e métricas mandatórias que devem ser totalmente atendidas para que o ciclo atual de homologação seja considerado encerrado com sucesso. Estes critérios garantem o rigor técnico e a maturidade mínima necessária antes de autorizar o avanço do produto para a próxima fase.

    O ciclo de validação será considerado apto para encerramento e aprovação quando:

    • 100% das funcionalidades descritas na Matriz de Rastreabilidade possuírem cenários de testes mapeados.
    • Todas as regras de negócio associadas aos requisitos passarem por validações de caminhos felizes e exceções.
    • Nenhum risco classificado como "Alto" ou "Crítico" permanecer sem a devida cobertura de testes ou plano de mitigação.
    • Os objetivos de qualidade inicialmente acordados pela equipe de testes para este ciclo forem atingidos.
    • A documentação dos Casos de Teste (CTs) estiver devidamente estruturada, revisada e vinculada aos IDs dos requisitos.

Suas diretrizes servem como fundação técnica obrigatória para guiar a modelagem e a futura execução dos cenários de teste na próxima etapa da disciplina.

    📖 Glossário da Aula

    QA
    Quality Assurance — processo de garantia de qualidade de software. Envolve planejamento, execução e prevenção de falhas.
    Homologação
    Ambiente controlado onde o software é validado antes de ir a produção. É o espaço do QA.
    Caso de Teste
    Documento que descreve pré-condições, passos, dados de entrada e resultado esperado para validar uma funcionalidade.
    Defeito (Bug)
    Divergência entre o comportamento real do sistema e o comportamento esperado, documentada com passos para reprodução.
    Happy Path
    Cenário onde tudo funciona conforme o esperado, com dados válidos e fluxo ideal. É o "caminho feliz" do teste.
    Sad Path
    Cenário com dados inválidos, fluxos inesperados ou violações de regras. Revela a maioria dos bugs reais.
    Severidade
    Classificação do impacto de um defeito no sistema: Crítico (S1), Alto (S2), Médio (S3) e Baixo (S4).
    Requisito
    Descrição formal do que o sistema deve fazer (funcional) ou como deve se comportar (não-funcional).
    Regra de Negócio
    Restrição ou condição que o sistema deve respeitar para atender às necessidades do domínio do problema.
    Plano de QA
    Documento que define objetivos, escopo, estratégia e responsabilidades do trabalho de teste em um projeto.
    In Scope
    O que está dentro do escopo do teste — funcionalidades e regras que serão verificadas.
    Out of Scope
    O que está fora do escopo do teste — aspectos que não serão verificados neste ciclo, com justificativa.
